# Proof-carrying frontier

The proof-carrying frontier is the release gate for Type-4 expansion. It turns
"this looks like the next semantic clone axis" into a stricter question:

> Is there enough linked evidence to open exact semantic admission without
> weakening nose's zero-false-merge contract?

The answer is recorded in the machine-readable [`proof_carrying_frontier.v1.json`](../bench/type4/proof_carrying_frontier.v1.json)
artifact and the companion [`proof_carrying_frontier.md`](../bench/type4/proof_carrying_frontier.md)
report. Roadmap triage starts from the compact generated
[`frontier_readiness.md`](../bench/type4/frontier_readiness.md) artifact, with
[`frontier_readiness.v1.json`](../bench/type4/frontier_readiness.v1.json) as its
machine-readable form. The proof/readiness files are generated by the
[`proof_carrying_frontier.py`](../bench/type4/proof_carrying_frontier.py) checker;
the executable witness report is generated by `type4-exec-check`.

## Inputs

The report reads five evidence layers:

- `frontier_target_packets.v1.json` - curated target packets selected from the
  corpus-balanced frontier platform.
- `real_frontier.v1.json` - human-verified evidence records with semantic claims,
  proof invariants, detector status, and hard negatives.
- `bench/coevo/packets.v1.json` - adversarial co-evolution packets, verdicts, and
  defenses across claim surfaces.
- `bench/type4/adversarial/cases/cases.v1.json` - focused positive cases,
  hard-negative cases, and packet-level hard-negative groups.
- `bench/type4/executable_expectations.v1.json` - the stable JSON report from
  `type4-exec-check`, proving which declared focused-case expectations were
  replayed by a real `nose query` binary.

The target packet may repeat evidence fields for review convenience, but the gate
checks that those fields still match the linked `real_frontier` record. If the
semantic claim, proof invariant, hard negatives, or detector result drift, the
artifact check fails.

The hard-negative group check is stricter than "has some negatives": every target
packet must cite a packet-level group, and that group must keep positive focused cases,
hard-negative focused cases, and regression gates together. Convention IDs cover the
numeric, boolean, loop, collection, and protocol-boundary classes so new packets inherit a
named soundness perimeter instead of inventing one-off prose.

Executable witness coverage is tracked separately from manifest linkage. A packet can
link focused cases and still be blocked if its declared executable expectations are
missing, stale, or failing. `ready-for-defender` rows and detector-admitted rows require
fresh coverage for every declared expectation in the packet perimeter.

## Admission Policy

An exact-admission packet is ready only when it has all of:

- linked `real_frontier` evidence whose primary status is `real-miss`;
- a narrow proof invariant;
- adjacent hard-negative siblings;
- packet-level hard-negative group linkage;
- fresh executable focused-case witness coverage for declared expectations;
- a current detector result that shows the present boundary;
- no unresolved proof, soundness, or product blockers;
- product-output and runtime evidence before merge.

Adversarial co-evolution is guardrail context. A green or fixed co-evolution
campaign does not by itself open exact admission; it only strengthens the case
that the packet's claim surface has been attacked.

## Commands

Regenerate the committed artifacts:

```sh
NOSE_BIN=target/debug/nose bench/type4/adversarial/scripts/type4-exec-check \
  --stable-report \
  --json-out bench/type4/executable_expectations.v1.json
python3 bench/type4/proof_carrying_frontier.py
```

Check that the committed artifacts are current:

```sh
python3 bench/type4/proof_carrying_frontier.py --check
```

Run corpus-free checks for the validator itself:

```sh
python3 bench/type4/proof_carrying_frontier.py --selftest
```

The docs gate runs `--selftest` and `--check`, so stale proof-carrying frontier
and readiness artifacts fail before merge.

## Relationship To Other Type-4 Tools

- [frontier platform](frontier-platform.md) ranks and curates Type-4 target
  packets from corpus evidence.
- [adversarial co-evolution](adversarial-coevolution.md) attacks claims and
  records fixed, refuted, deferred, and green packets.
- [formal soundness](formal-soundness.md) owns the Lean obligation registry for
  proof-sensitive semantic rewrites.
- [Type-4 focused cases](type4-adversarial-coverage.md) maintain focused
  positive and hard-negative fixtures around target packets.

The proof-carrying frontier report is the admission summary above those layers:
it does not find new candidates, and it does not certify a proof. It tells the
project whether the evidence package is ready to let a detector PR open exact
semantic behavior.
