## `numeric.clamp.proven-integer-bounds`

**Proof-backed integer clamp**

Integer clamp surfaces are equivalent only when they compute the same bounded value and source evidence proves both integer-domain operands and lo <= hi bound order.

- status: `controlled-slice-admitted`
- rationale: The numeric-clamp packet already has a proof-carrying perimeter, modeled facts, focused positives, and hard negatives; recording it as a semantic pattern makes future language surfaces attach to the same invariant instead of to min/max or method-name spelling.
- required facts: `numeric-clamp.integer-domain`, `numeric-clamp.bound-order`
- hard-negative templates: `numeric.unordered-bounds`, `numeric.swapped-bounds`, `numeric.float-nan-domain`, `protocol-boundary.method-name-only`, `numeric.wrong-minmax-shape`
- boundaries: unordered or swapped bounds are not clamp-equivalent; float or NaN-sensitive domains stay outside this integer clamp pattern; method names alone do not prove library clamp semantics; custom clamp-shaped APIs need receiver, domain, and bound-order evidence
